## 更正：Halo 授权接口是「替换」语义 + 修复登录降权（16:20）
- **上一节「追加语义」的结论是错的**。错因：先授 super-role 再授 guest 时，guest 请求实际返回 **400「检测到有重复的名称」**，我把「角色仍是 super-role」误读成「追加成功」。本次重测拿到响应体才发现。
- **正确语义**：`POST /users/{name}/permissions` body `{"roles":[...]}` 是**整体替换**。三重证据：① Halo 日志 `Updated roles for user: existingRoles=[A], roles=[B]`；② RoleBinding 命名 `<user>-<role>-binding`，替换时旧 binding 被 `GcReconciler` 删除；③ 请求集合含已有角色名 → 400「名称重复」。请求 `[guest,post-author]` → 结果 `["post-author","guest"]`，即替换为集合内容。
- **真正的病根**：`unified_login.create_halo_user` 每次登录无条件 `_grant_role(username, halo_role)`。fengyukai 论坛侧是 student → 映射 guest，于是**每次登录都把 forum-13 的 super-role 冲成 guest**。halo.log 铁证循环：`15:31:25 [guest→super-role]`（手工授）→ `15:39:16 [super-role→guest]`（用户登录）→ `16:07:11 [guest→super-role]`（又手工授）→ `16:13:31 [super-role→guest]`（又登录）。所以用户看到的永远是访客。
- **修复**：`unified_login.py` 新增 `ROLE_RANK`（super-role 100 / post-author 50 / guest 10）、`get_user_roles()`、`_max_role_rank()`、`_highest_role()`、`sync_role()`。`sync_role` 仅在「目标角色等级 ≥ 本地现有最高等级」时写入，否则跳过 → **登录永不降权**（自动升级保留，手工降权需去控制台）。
- **同时修正误导字段**：BFF 响应新增 `effective_role`（登录后实际生效角色）。原 `halo_role` 是论坛映射值（guest），与实际生效（super-role）不符，极易误判。前端只用 `halo_username`，无兼容问题。
- **部署通道坑**：`dpl.py push` 的 tar 内需保留 `halo-cn/` 前缀（在 `output/plaza-20261103` 下 `tar czf x.tgz halo-cn/gateway/xxx.py`），远端用 `tar xzf - -C /opt/plaza --strip-components=1` 剥离。`tar czf` 的**本地路径不能写盘符**（`C:` 会被 tar 当成远端主机名报 `Cannot connect to C:`），必须 cd 到目录用相对路径。
- 备份 `/opt/plaza/backup/login-nodowngrade-202611061610/`；md5 本地=线上 `f1b0d9f7...`(unified_login) / `0b851a42...`(login_server)；`/usr/bin/python3.11 -m py_compile` 通过；`systemctl restart login`。
